# Architecture

The public static website and Next.js `operations/` application remain separately built and deployed. Sarathi Business Manager is a modular monolith using React, Better Auth, PostgreSQL and parameterized `pg` SQL. The provider/authentication architecture is unchanged; Milestone 4 adds server-side PDFKit and compatible dependency security patches.

## Authenticated organization boundary

`server/identity.ts` resolves the current uncached Better Auth session and active global user. `server/tenancy.ts` reuses the existing permission intersection to resolve an active organization membership and permitted active divisions. With no tenant switcher, the server chooses the first active membership by organization ID; browser actor/organization/division headers and form fields do not establish context. `getActor` exposes the effective membership-capped role. Global ADMIN does not bypass membership.

Every existing business entry in `server/dal.ts` and `server/workflow.ts` obtains a `TenantPool` from `authorizedDatabase`. `server/lists.ts` and `server/business.ts` require that scoped type. The pool facade checks out a connection, begins a transaction, rejects owner/superuser/BYPASSRLS configurations, revalidates membership/permission, and binds actor, organization, permission and default division using `set_config(..., true)`. Reads commit after their statement; conversion/stage changes use their existing multi-statement transaction. No tenant state is kept on module globals or shared pooled sessions. Commit/rollback reset LOCAL values; unreleased open transactions cause connection destruction.

Migration 007 adds ownership and RLS to all ten existing business tables. PostgreSQL policies scope root records, aggregates, correlated subqueries and parent-derived records together. Guards recheck active user/membership/organization/division assignments per statement. Mutations additionally require the authorized operation and non-viewer roles; migration 007 added no delete or financial-write policy/grant. Milestones 4 and 5 add narrowly scoped quotation and append-only payment writes; cost/BOM writes remain unavailable. Raw unscoped runtime reads return no records, and writes fail closed. Explicit staff queries use the current organization membership join; the staff role function verifies transaction-bound actor/organization, locks the organization, and checks current admin membership.

## Data integrity and preserved workflows

Migration 006 supplies organizations, divisions, memberships and assignments. New migration 007 backfills Sarathi ownership and Smart Solutions lead/project divisions through constant ADD COLUMN defaults, preserving frozen quotation snapshots, append-only history, timestamps and original service arrays without UPDATE or disabling triggers. Composite foreign keys constrain customer/lead/project/quote/payment/product/actor relationships. Runtime inserts receive ownership only from transaction-local server context. Conversion preserves the source lead division and attributes audit rows to the authenticated actor.

Customers are organization-wide; operational projects/leads, explicit-division quotations, and parent-derived payments/history are division-restricted. The current forms create in permitted Smart Solutions, or the sole permitted division if Smart Solutions is unavailable. Ambiguous assignments without Smart Solutions have no implicit write default. A future explicit authorized division selector must precede broader division workflow UI. The service catalog is public configuration; saved project service IDs remain owned within the project.

Staff listing/role assignment is organization-scoped. Single-membership role updates preserve current behavior; shared identities retain their global ceiling, and raising that ceiling needs owner authorization so another organization's capped membership cannot be activated accidentally. Provision/recover CLI tools select `SARATHI_ORGANIZATION_SLUG` (default `sarathi`) and require active target organization/membership/division as applicable. Credentials remain identity-owned, so owner recovery revokes all sessions of the selected identity, including other memberships.

No invite/division-assignment/revocation/removal UI or public file-storage module is introduced. Customer editing, quotation documents and manual payment records are implemented by the modules below. Owner-only metadata administration remains outside the runtime grant boundary. Additional organization onboarding remains disabled pending staging review. See [coverage](TENANT_ISOLATION_COVERAGE.md), [database design](DATABASE_DESIGN.md), [security](SECURITY_MODEL.md) and [progress](DEVELOPMENT_PROGRESS.md).

## Customer Management V2 — Milestone 3

The existing customer list, creation action and project selector remain in place. `server/customer-mutations.ts` implements creation/editing through the same authenticated DAL and `TenantPool`; `server/transaction.ts` shares the existing transaction/timeout/rollback helper with lead/project workflows. New customer profiles at `/admin/customers/[id]` use `server/customers.ts` and existing business relationships, rather than copying operational records into another customer-history store.

Migration 008 adds a stored normalized phone with an organization/phone index, an edit version, and organization/actor/UUID submission metadata. Original phone formatting remains unchanged. Indian mobile prefixes (+91, 0091, leading 0) normalize together; landline/international codes otherwise remain distinct. Every browser/DAL creation supplies a UUID v4 retained for uncertain-save retries. A transaction serializes that organization/actor/request and the organization/phone, checks the saved payload hash, and either returns the prior record, warns about duplicates, or inserts once. Direct unkeyed persistence calls remain available only for trusted internal fixtures/imports; they are not an authenticated creation path.

Duplicate detection is advisory: exact normalized phones are strong matches; normalized names of at least four characters matching exactly or as a prefix are possible matches. SQL normalizes both name operands consistently. Results are restricted by customer RLS, capped at ten and ordered with phone matches first. Staff may explicitly confirm a different customer, with no merge or destructive overwrite. Editing uses a row lock and submitted version; a stale save fails. Only name, phone, email and address can change. Database triggers increment the version/time and append changed field names and the authenticated actor atomically. No-op saves leave the version/history unchanged. Existing `status_history` remains the source for project progression.

Profiles show contact information and paginated tabs for existing leads (including converted leads), projects/services/stages, recent activity, quotations and permitted payments. Each query is bounded to 26 rows, displays 25 and uses a validated timestamp/source/bigint cursor. Division labels, counts and service IDs come only from RLS-visible records. Customer changes are organization-wide; project history remains restricted by its parent division. Exact quotation/payment decimals are displayed as recorded; no inferred balance, future follow-up or fabricated total is introduced. Existing quotation snapshots and payment immutability are unchanged. The reusable create/edit form uses the current styles and a native dialog for keyboard focus containment, with validation, loading/error/success feedback.

## Milestone 4 quotation module

`server/quotations.ts` owns authenticated readers, editor metadata, preview and transactional lifecycle persistence through the existing `authorizedDatabase`/`TenantPool`. `quotation-input.ts` validates bounded DTOs and owner-verified tax profiles; `lib/quotation-money.ts` uses exact BigInt paise and the existing commercial engine. The engine deployment copy is synced by existing site synchronization or `npm --prefix operations run sync:commercial`, with a parity test.

Migration 009 extends existing quotations/items without updating legacy financial content. Standalone offers have explicit division/customer ownership and optional composite-owned project links. Request hashes, draft versions, family/project serialization, numbering counters and one-baseline indexes control retries/concurrency. Immutable events and private JSON/PDF artifacts are transactionally written before issue commits. `server/documents/a4.ts` is the shared page/font/wrapping foundation; quotation and payment renderers reuse it. Secure download returns stored bytes through a Node route; no public object storage or browser credentials are introduced.

The editor, lifecycle controls and bounded event/version history reuse current components/styles and the service catalog. Existing customer and project readers include standalone offers through LEFT JOINs. Staff decision records and optional Procurement progression use existing stage/reason validation without recording payment. [Quotation usage and release prerequisites](QUOTATION_USAGE.md) document money policy, immutable snapshots, legacy limitations and the exact local walkthrough.

## Milestone 5 manual payments

`server/payments.ts` owns payment readers, target lookup, receipt/refund/correction persistence, allocation and balance calculations through `authorizedDatabase`/`TenantPool`. `payment-input.ts` bounds methods, references, reasons and timestamps; `lib/payments.ts` uses exact BigInt paise, including aggregates beyond the per-entry limit. Project receipts can precede a quotation; standalone receipts require an accepted quotation in the same composite-owned family/division/customer.

Migration 010 adds immutable private documents, signed allocations and events without updating original financial rows. Numbering, payment, frozen snapshot, PDF/hash and audit commit atomically; deferred guards reject a payment without its matching artifact. Project/family and original-receipt locks serialize quotation baselines, refunds and allocations. Positive allocations consume an existing receipt, while refunds/corrections consume unallocated value first and append negative allocations where necessary. Corrections use a separately labelled reversal, preserving the original receipt and distinguishing them from actual refunds.

Current balances use all scoped receipts less refunds/corrections and the current accepted baseline, with outstanding and credit shown separately. Allocation does not add another cash movement. Historical allocations and stored documents do not change when a quotation is revised or a customer is edited. A shared server component supplies permitted project/quotation summaries; payment list, detail/history and private PDF routes reuse current layouts and styles.

The client retains only a pending request UUID in sessionStorage. An interrupted response can be retried with the same hash or recovered after reload through an authenticated actor-scoped lookup. UUIDs establish no permissions. Receipt and allocation recovery avoid duplicate ledger entries without persisting customer/form data in browser storage. See [payment usage](PAYMENT_USAGE.md) and [verified progress](DEVELOPMENT_PROGRESS.md).
