# Security model

Reuse Better Auth private sessions, closed registration, MFA/recovery, exact-origin/CSRF checks, bounded input, parameterized SQL and safe DTOs. Database credentials, tokens, SQL parameters and customer data must never appear in client code or logs. Tests use generated identities and disposable PostgreSQL, never configured databases.

## Tenant isolation

- Identity comes from the current uncached session and active user. Membership, organization, role intersection and division assignments are verified in the existing resolver. Global ADMIN without membership is denied; VIEWER never writes. OPERATOR is also the current manager-like role, not a new role. Milestone 5 receipt/allocation writes require explicit operator membership authorization; refunds and receipt corrections require effective organization ADMIN.
- Every business read/write obtains a scoped database facade. Each checkout starts a transaction, reauthorizes, rejects owner/BYPASSRLS roles, and binds LOCAL actor/organization/permission values. The runtime role must not own tables or belong to owner roles. The grant recipe rejects bypass roles. Never route business reads through the raw authentication pool.
- RLS scopes organization-wide customers/products and division-owned leads/projects; related quotation, payment, history, costing and item rows inherit parent visibility. Standalone quotations/payments have explicit division ownership. Nested counts/search/activity queries therefore share the boundary. Active-state/assignment checks run per statement; previously returned scope objects cannot authorize after revocation. Raw unbound runtime reads return no business rows. Runtime has no delete, financial UPDATE, private costing-read or metadata-write grants; current quotation and payment INSERT grants are narrow and operation-bound.
- Composite ownership FKs block foreign customers, leads, projects, quotes, products and staff references independently of server checks. Audit actor must match the authenticated transaction actor. Frozen documents, payments and history remain immutable. Ownership defaults have no fallback organization outside a bound transaction.
- Staff lists join only the selected organization's memberships. Role changes use a scoped security-definer function with fixed search path, current admin checks, organization lock and self-demotion protection. An active acting admin always remains; admins cannot change another organization's membership. Shared identity ceiling increases require privileged owner authorization. The old global role-change function is revoked from the runtime role when the latest grants are applied.
- Provision/recover are owner-only tools with active organization selection and transactional rollback. Runtime cannot invite, assign divisions, revoke or remove arbitrary memberships. Identity security/onboarding endpoints affect only the authenticated identity; owner recovery deliberately revokes all that identity's sessions.

## Verification and release gate

The isolated suite covers two organizations with overlapping records, direct HTTP/actions/DAL/persistence paths, foreign IDs/references, division restrictions, revoked sessions/memberships, shared staff role changes, viewers, financial reads, pool reuse and owner misconfiguration. The upgrade fixture compares every original field in all ten tables, including issued quotations and append-only history, and injects a failure to verify rollback. Actual command results are recorded in [progress](DEVELOPMENT_PROGRESS.md).

Owner/superuser credentials are intentionally privileged and outside the application-user threat model. Do not distribute runtime credentials to applicants/staff or expose direct database access. Future tables/routes require explicit ownership, policies/grants and cross-organization tests before release. No public exports/files/delete path currently exists.

Additional organizations remain disabled. Actual hosted transaction-pool compatibility, edge/session security, TLS, reviewed runtime grants, backup restore and staging upgrade remain unverified. Migration 007 and new grants must precede the corresponding app in a controlled release; rolling back to a pre-isolation app is not a supported recovery because unscoped reads become empty and inserts fail. Use reviewed restore/forward-fix procedures. Local passing tests do not authorize production deployment.

## Milestone 3 customer access and audit

Customer list/search/options/profile/duplicate/edit paths resolve active membership on the server and use the existing scoped pool. ADMIN and OPERATOR can edit their organization's customers; VIEWER cannot create or edit. Customers remain organization-wide. Profile-linked leads, projects, services, quotations, payments and stage activity follow the existing division/parent RLS. VIEWER payment tabs/queries are denied. Foreign customer detail IDs return unavailable/404, with no unauthorized duplicate or linked-record DTOs.

Migration 008 adds a customer UPDATE policy using `tenant_writable(...,'customers.update')`, preserves and strengthens the existing INSERT policy by binding keyed submission actors, and grants UPDATE only on the four contact fields. It does not change migration 007, expand financial/delete permissions, or accept browser organization/actor identities. Submission UUIDs and hashes are internal retry metadata, not authorization tokens, and are omitted from customer DTOs.

`customer_changes` has same-organization customer/actor FKs, organization RLS, SELECT-only runtime grants, and append-only/no-truncate triggers. A fixed-search-path SECURITY DEFINER trigger records meaningful changes in the same transaction. Runtime cannot inject, update or delete audit rows, change edit versions/ownership/submission identity, or omit an authenticated actor. Privileged owner maintenance is explicitly labelled when its audit actor is absent. Audit rows contain field names, actor, version and time, not duplicate old/new contact values. Existing owner/BYPASSRLS staging, credential and backup requirements remain release gates.

## Milestone 4 quotations and private PDFs

Every draft, preview, project picker, issue, revision, decision and download entry independently resolves the authenticated active membership and operation. Division IDs are validated against permitted assignments; they do not establish tenant identity. Composite FKs bind customer, optional project/division and revision family. New runtime inserts cannot masquerade as legacy rows to bypass required artifacts. Viewer writes, unassigned divisions, foreign IDs, forged organization headers and anonymous downloads fail closed.

Quotation/item writes are restricted to the existing quotation permissions and DRAFT parent. Issued content remains guarded by default-deny frozen-column/item rules. Runtime cannot delete quotations, alter document/audit rows, forge events, write ownership/creator or directly access numbering counters. A fixed-search-path scoped function allocates numbers; a bound-actor trigger appends decision/edit/issue events. RLS protects the new artifacts/events through their visible quotation parent. Artifacts may be inserted only for current drafts, and commit requires a matching stored issued snapshot. No payment/BOM/cost grants were added.

The issue transaction atomically includes number, exact validated snapshot, private PDF bytes/hash, lifecycle update and audit. Generation/storage/audit failures roll back; duplicate/concurrent issue or decisions cannot create another document/baseline. The download route rechecks current session/membership/division each time, returns attachment/no-store/nosniff and never exposes a public URL. Acceptance is explicitly staff-recorded communication, not customer authentication or a digital signature. Font assets contain no customer data and no external fetch occurs during generation. Hosted TLS, pool cleanup, backups/restore and storage growth still require staging verification.

## Milestone 5 payments, allocations and documents

Payment actions, retry lookups, balances, lists/history and downloads independently resolve active identity/membership/division through the scoped DAL. Effective organization ADMIN can record receipts and reasoned refunds/corrections; OPERATOR needs explicit `can_record_payments` membership authorization for receipts/allocations and cannot refund/correct. VIEWER has no payment access. Global ADMIN remains membership-capped. Previously resolved permissions fail after revocation.

Migration 010 adds operation-bound INSERT policies and narrow column grants, never financial UPDATE/DELETE, counter access or arbitrary event insertion. Composite ownership derives customer/division from the project or accepted standalone quotation. Runtime cannot supply recorder identity, organization, receipt number or recording time, create unkeyed legacy rows, move allocations across scopes, over-refund a receipt or commit without a matching immutable private artifact. Fixed-search-path scoped functions bind current actor and source ownership; locks serialize source caps and requests.

A receipt correction is an append-only reversal against a current receipt, labelled separately from a cash refund. Signed allocation reversals preserve history; privileged maintenance also remains subject to immutable/no-truncate triggers. Legacy financial rows are read-only and require owner reconciliation before retrospective corrections/documents. Number, snapshot, PDF/hash, payment and audit roll back together on generation/storage/audit failure.

Request UUID/hash metadata controls retries, not authorization. Browser storage contains only the pending UUID; recovery lookups require the same authenticated actor and current visible organization/division. Private PDF downloads reauthorize on every request and return attachment/no-store/nosniff/noindex. They expose stored bytes rather than rebuilding historic contact details. Linked refund/correction events are visible in the source receipt history. No gateway, money transfer, customer authentication, tax invoice, external sending or public document URL is introduced. Hosted pool/TLS, staging grants, print identity, backups/restore and artifact growth remain release gates.
